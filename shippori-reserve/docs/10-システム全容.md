### セキュリティ設計

- **RLS（Row Level Security）を全テーブルで有効**。読み書きは「在籍中のスタッフ」に限る
- 書き込みの多くは `security definer` 関数を通す（画面から直接テーブルを叩かせない）

- 個人情報は**来店日から13ヶ月**で氏名・電話・要望を自動消去（毎日12:00 JSTのcron）

## 4. 権限モデル

```ts
権限コード:
  reservation.read      予約を見る
  reservation.write     予約を作る・直す
  reservation.override  席ルールを上書きする
  businessday.write     営業日を設定する
  rule.write            席割りルールを編集する
  stats.read            集計を見る
  settings.write        店の既定値を変える
  account.write         アカウントを発行・停止する
  audit.read            監査ログを見る
  shift.write           確定シフトを組む
  shiftrequest.write    希望シフトを出す
  sales.write           売上の目標・実績を入力する

ロール:
  owner   = 全部
  manager = 全部（account.write を除く）
  staff   = reservation.read / write / override, stats.read, shiftrequest.write
  viewer  = reservation.read のみ
```

**設計の意図**：オーナー・店長は「シフトを組む側」（`shift.write`）、一般スタッフは「希望を出す側」（`shiftrequest.write`）。店長は希望を提出しない（店主の指定）。

## 6. 業務ルール（ここが設計の核心）

この章がいちばん重要です。**すべて店主の実務判断から来ています**。

### 6-1. 売上には「物差しが2つ」ある

日本の消費税は、店内で食べれば10%・持ち帰れば8%（軽減税率）。**エアレジの税率別集計が、そのまま「店内飲食」と「物販」の境目になります。**

| 見るもの | 使う数字 |
|---|---|
| 日ごとの表示・その日の目標達成の判定 | **店内だけ**（＝実績 − 物販） |
| 月間の合計・月間目標の達成 | **物販こみの合計** |
| 物販そのもの | 別枠のカードに出す |

**なぜ**：うなぎの太巻きのような物販が1日で62万円入ると、その日の売上が通常営業の5日分になり、平均・前年比・目標の達成判定が全部そこに引きずられます。日ごとを店内だけで見れば店の地力がそのまま読め、稼いだお金は月間にちゃんと乗ります。

読み替えは `src/lib/sales.ts` の `salesView()` / `hitOf()` の**1か所だけ**で行います（画面ごとに答えが違う状態を作らないため）。

### 6-2. 客単価

- 客単価 ＝ **（売上 − 物販）÷ 客数**（物販は除外・店主指示）
- **客単価は保存しない**。客数と売上という事実だけ持ち、割るのは表示のとき。保存した平均は、あとで実績を直したときに置いていかれて必ず食い違う
- 分子と分母は**同じ日ぶんに揃える**。客数が月の半分しか取り込めていない月に、月まるごとの売上を客数で割ると客単価が倍に見える
- 直せない歪みが1つ：分母の客数には**持ち帰りだけのお客様も入っている**（エアレジは税率別の客数を出さない）。太巻きの日を含む月は客単価がやや低めに出る

### 6-3. 席のルール

- **1つの席は1晩1組**。時間帯での回転は見ない（一度実装して撤去した。実際の運用と合わなかった）
- カウンターだけは相席可で、1席ずつ埋まる
- 席メモは `'T1＋T2'` のように**全角＋区切りの文字列**で持つ
- **貸切**（`is_exclusive`）の日は店ごと押さえる。あとから席を1つだけ入れることはできない
- 二重予約は**3段階**で止める：
  1. 画面で選べなくする
  2. サーバー（Server Action）で保存前に確認する
  3. **DBのトリガーで最終的に止める**（`assert_seat_free()`。`pg_advisory_xact_lock` で同じ営業日の書き込みを直列化し、ネット予約とスタッフ側で同じ鍵を使う）

### 6-4. 席ボードの下書き（自動配置）

席ボードには、その日の予約から**自動で下書き**が並びます。席は3つの状態を持ちます。

| 見た目 | 意味 |
|---|---|
| 白 | 空き |
| **点線＋姓** | 予約（まだご来店前）。予約から自動で作った下書き |
| 塗り | 着席（タップして点けた席） |

カウンターの案内の法則（店主から聞き取り。`src/lib/seat-plan.ts`・テスト20件で固定）：

| 組の人数 | 案内する順番 |
|---|---|
| 1名 | 3 → 4 → 5（真ん中に寄せ、両端と一角を組のために空ける） |
| 2名 | 1・2 → 6・7 → 3・4（真ん中は最後。先に使うと長い辺が分断される） |
| 3名 | 8・9・10 → 1・2・3 → 5・6・7（折れた先の一角にまとまる） |
| 4名以上 | 10 → 9 → 8 …（角をまたいで続きの席が取れる） |

**和室には自動で入れない**（指定して取るお席なので、下書きが埋めると「空いていないように見える」害だけが出る）。

**下書きはDBに保存しない**。保存すると「予約が入っている席」と「本当に座っている席」の区別がつかなくなるため、毎回予約から作り直します。

### 6-5. 営業時間と「LAST」

- 通常営業：18:00〜24:00（**金土は25:00**）
- イベント営業（ビアホール等）：18:00〜24:00・**席ではなく定員36名で管理**
- 時刻は「0:00からの経過分」で持つ（25:00 = 1500）。**営業日は4時締め**なので、金曜25時の売上・予約は「金曜」として扱う
- シフトの「LAST」は `end_min = null` で持ち、表示するときにその日の `close_min` を当てる。**25:00 と書き込まない**（営業時間を変えた日にシフトだけ古い時刻で残るため）

### 6-6. シフト

- 毎月**25日締切**で翌月分の希望を提出（◯×をタップするだけ）
- 店長が確定 → 確定した月だけカレンダーに出る（組みかけの下書きは見せない）
- 人ごとの基本の出勤時間を持ち、◯を押した日に自動で入る（提出の簡単さは変えない・店主指示）

| | 基本の時間 |
|---|---|
| 金本 | 19:30〜LAST |
| 安藤 | 18:00〜20:00（日月は普段お休み） |
| 白石 | 18:30〜LAST |
| 高木 | 19:00〜LAST |
| 安井 | 18:30〜21:00 |
| 店長・オーナー | 時間を持たない |

**3つの状態を取り違えないこと**（判定は `src/lib/shift-time.ts` の1か所）：

| 状態 | 持ち方 |
|---|---|
| 時間の概念を持たない人 | `profiles.default_start_min` が null |
| その日は基本のとおり | 行の `start_min` が null |
| その日だけ違う | 行に時刻が入っている（`end_min` の null は LAST） |

**触った日だけ記録する**（基本の時刻を毎回書き込むと、あとで基本を変えたときに古い時刻が残る）。

### 6-7. 流入元（`source`）

集計の根幹なので**必須**です。`owner_direct`（オーナー経由）のときは「どのオーナー経由か」まで持ちます。オーナー3名がそれぞれ客を持っているため、誰の紹介が売上にどう効いているかを見たいという実務要求から来ています。

## 7. ネット予約の流れ

```
お客様
  └ shipporitei.jp/reserve（または Instagram のリンク）
      └ yoyaku.shipporitei.jp/yoyaku
          日付 → 時刻（15分刻み・22:00まで）→ 人数 → 席 → お名前・電話 → 送信
              │
              ├ 空き判定：その日の予約＋席ボードの実際の着席状況＋自動下書き
              ├ 繁忙日（金土は自動）のルールを強制
              ├ ハニーポット・同一電話3件制限・全体レート制限
              ├ 貸切の日／ネット予約停止中の日は受け付けない
              │
              └ 登録（**status = confirmed**, source = web_form）
                  ├ 予約番号（R-2608-0142）を画面に出す
                  ├ 「ご予約が確定しました」と表示（仮予約ではない）
                  ├ **公式LINEグループへ通知**（週次レポートと同じグループ）
                  └ 席ボードのタブレットに音つきの全画面お知らせ（タップするまで消えない）

キャンセル
  └ /yoyaku/cancel で 受付番号＋電話番号 の一致を確認 → キャンセル
      └ **公式LINEグループへ通知**
```

**その場で確定する**（店主判断）。お客様を待たせず、店の折り返しの手間も無くなる。
**そのぶん、席は送信の瞬間に押さえられる**ので、いたずら予約は席をそのまま奪う。
入口の本人確認（SMSまたはLINE）が要るのはこのため。

## 8. 外部連携

### 8-1. エアレジ（売上・客数の取り込み）

**エアレジには公開APIがありません。** なのでPlaywrightでブラウザを自動操作しています。

- ログインはセッションCookie。`scripts/airegi-login.mjs` で一度ログインして `storageState` をJSONに保存し、以降はそれを注入して復元
- セッションは数時間〜で失効しうる。失効したらLINEで「再ログインしてください」と通知
- 日別売上の一覧から：日付・売上・**会計数**・**客数**・商品数
- 各日の「詳細」から：**税率別**（10%＝店内 / 8%＝物販）
- 詳細画面はハッシュルート（`#/detail/year/2026/month/07/day/26`）のSPA。`page.goto` では画面が切り替わらないので、ハッシュを書き換えて**その日の日付が画面に出るまで待つ**
- 読めた日だけ送る。**0は送らない**（「読めなかった日」と「0だった日」は違う）

送り先：`POST /api/sales/ingest`（`x-api-key` ヘッダ）。渡さなかった項目は既存の値を保つ。

### 8-2. LINE（公式アカウント / Messaging API）

同じグループに3種類が流れます。

1. **週次レポート**（週1）… 先週の売上・客数・客単価・曜日別・人件費・目標達成率・HPアクセス
2. **ネット予約が入った**（都度）
3. **ネット予約がキャンセルされた**（都度）

送信は失敗しても本処理を止めない（`console.error` して先へ進む）。通知が落ちても予約は通る、という順序です。

### 8-3. GA4（アクセス解析）

- 公式サイトと予約ページの両方に入れてある
- 予約ページは `page_location` を**パスだけに差し替えて送る**（既定だとクエリ文字列ごと送られ、そこに個人情報が乗りうるため）
- 公式サイトの `/dashboard` に、GA4の数字と予約の**集計だけ**（氏名・電話は含まない）を出す
- GitHub Actions が毎時ビルドして自動更新

### 8-4. freee人事労務

週次レポートの人件費（会社ID 12248050）。OAuthトークンをローカルに保存して使う。

### 8-5. Twilio（SMS本人確認）

無断キャンセル対策として実装済み。稼働は未定（1通約10円）。

## 8-6. LINE連携（LIFF・2026-08-19 実装）

**公式アカウントは2つある。** ①「しっぽり亭レポート」＝店内向け（週次レポート・各種通知）、
②「しっぽり亭 家庭料理おばんざい居酒屋」＝お客様向け（友だち追加してもらうのはこちら）。
送り先ではなく「どのアカウントから送るか」で届くかが決まるので、トークンは分けてある。

- **LIFF**：予約ページをLINEアプリの中で開くと、ログインと同時に②の友だちになり、
  予約とLINEのIDが結びつく（`reservations.line_user_id`）。友だち追加「だけ」では紐づかない
- **なりすまし防止**：ブラウザから来たIDは信じない。IDトークンをサーバーでLINEに検証させ、
  返ってきたIDだけ保存する
- **LINEで確認できた人にはSMSを送らない**（本人確認として同じ役目。2回証明させない）。
  トークンの期限切れ・LINE障害のときはSMSに切り替わり、予約は必ず通る
- **お客様への自動送信**：予約の控え（即時）／前日リマインド（19時・当日予約は除く）／
  静かな日のクーポン（13時・予約ゼロの日だけ・7日間隔・月4回まで・スイッチ制）
- **通数の守り**：無料プラン200通。控え60通ぶんを常に温存し、リマインド・配信が譲る。
  配信は「友だちの人数ぶん」を一気に使うので、残数が読めないときは送らない
- 友だちの出入りは webhook で `line_friends` に記録（ブロックは行を消さず印を付ける）
- **webhook導入前からの友だちは名簿に載っていない**（生ビールクーポンで集めた方々）。
  この人たちも LIFF予約・控え・リマインドは全部ふつうに動く。名簿に行ができるのは
  「ブロックした」「トークに書いた」「（再）追加した」のいずれかのとき。
  だから友だちの**人数**を名簿で数えてはいけない——数えるときは必ずLINEの統計APIに聞く

## 8-7. バックアップ（2026-08-18 実装）

Supabase Freeにはバックアップが無いため、**店主のMacが週1回（月曜8時）全テーブルを
JSONで書き出して iCloud Drive に置く**（`GET /api/cron/backup`＋`shippori-report`）。
直近8世代＋各月1本（13か月で消える・お客様への約束と揃える）を保持。成功も失敗も毎週LINEに1行。復元は `restore.mjs`

## 10. 設計方針（なぜこう作ったか）

この5つが、判断に迷ったときの基準です。

1. **iPhoneの片手操作が基準**（375×667に収まらないものは設計が間違っている）。主要操作は親指の届く下半分で完結させる
2. **画面ごとに答えが違う状態を作らない**。売上の読み替え・席の判定・シフトの時間解決は、それぞれ**1つの関数**を全画面が通る
3. **古いデータを見せるくらいなら少し遅いほうがマシ**。予約データはキャッシュしない（Service Workerがキャッシュするのは見た目の部品だけ）。オフライン書き込みも作らない（二重予約の温床になる）
4. **事実を持ち、解釈は表示のときにする**。「税率いくらの売上がいくら」という事実を持ち、店内/物販への読み替えはアプリ側で行う。客単価のような割り算は保存しない
5. **店主が壊れたことに気づける**。取り込みが止まればLINEに通知が飛び、画面には「◯日までの数字です」と締め日が出る
