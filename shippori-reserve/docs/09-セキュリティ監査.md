## 個人情報がどこに置かれているか（法28条・2026-08-17）

事故が起きたとき「どこに何があるか」を探しながら考えるのは無理なので、先に書いておく。

| 何が | どこに | 所在地 |
|---|---|---|
| 氏名・電話番号・メモ（予約） | Supabase（PostgreSQL）`ytqjgomnktkmoddidypd` | **東京**（AWS `ap-northeast-1`） |
| 同・アプリの処理中 | Vercel の関数 | 東京（`vercel.json` の `regions: ["hnd1"]`） |
| 電話番号（認証SMSの宛先） | Twilio Verify | **米国**。予約ページに明記済み |
| 氏名・電話（監査ログ） | 同 Supabase の `audit_logs` | 同上。**値はマスク済み**（0033） |
| 予約の集計（氏名・電話なし） | 公式サイトのダッシュボード（Cloudflare Pages） | 集計値のみ。個人情報は出力しない |
| 予約ページの閲覧記録 | Google アナリティクス（GA4） | **米国**。ページのパスと人数だけ。氏名・電話・予約番号・キャンセルの合言葉は送らない。予約ページに明記済み |

つまり**予約者の氏名と電話番号は日本国内にある**（Supabase 東京・Vercel 東京）。
国外に出るのは Twilio に渡す電話番号だけで、それは予約ページに明記してある。
法28条（外国にある第三者への提供）で説明が要るのは Twilio のぶんだけ、という整理。

補足：
- 予約者の氏名・電話は**来店から13か月で自動的に消える**（`purge_reservation_pii()`・毎日12時）
- 消えるのは連絡先だけで、人数・時刻・流入元・席・状態は残る（売上と集計に影響しない）
- Twilioに渡るのは電話番号だけ。氏名・メモ・アレルギーは渡していない

## 1. [critical] SMS認証送信APIが完全に無制限（SMS爆撃・Twilio課金の踏み台）
- 場所: /home/user/abet-news/shippori-reserve/src/app/api/public/sms-start/route.ts:15
- 攻撃: 認証もCAPTCHAもレート制限も一切なし。誰でも今すぐ実行できる:

  curl -X POST https://yoyaku.shipporitei.jp/api/public/sms-start \
    -H 'content-type: application/json' -d '{"phone":"09012345678"}'

これで実SMSが飛ぶ。phone を 09000000000〜09099999999 で回すだけのループを書けば、1台のPCから毎分数百通。route.ts のコメントは「再送間隔・試行回数の制限はTwilio Verify側が行う」としているが、Twilio Verify のレート制限は『同一電話番号あたり』であって、番号を変える攻撃には一切効かない。src/lib/public-booking.ts:398 の startSmsVerification は normalizePhone で桁数を見るだけで、IP・回数・総量をどこにも記録していない（grep で確認: リポジトリ全体に x-forwarded-for もレート制限テーブルも存在しない）。TURNSTILE_SECRET_KEY / NEXT_PUBLIC_TURNSTILE_SITE_KEY は .env.local.example に用意されているが src/ のどこからも参照されておらず、ボット対策は NetBooking.tsx のハニーポット欄だけ。ハニーポットは /api/public/reservations にしか無く、このAPIには関係ない。
- 影響: Twilio Verify は1認証試行ごとに課金され、加えて日本のSMS単価がかかる。放置すれば数時間で数万〜数十万円が店の Twilio アカウントから溶ける。金銭被害だけでなく、無関係の第三者の携帯に「しっぽり亭」名義の認証SMSが大量に届き、苦情・キャリアからのスパム認定を招く。さらに SMS pumping（攻撃者が提携する高額着信番号帯に送らせて分配金を得る）の踏み台にされる典型形。最後に、Twilio 残高が尽きた時点で smsEnabled() は真のままなので、正規のお客様が認証コードを受け取れず予約が丸ごと止まる。オーナーは非エンジニアで、請求が来るまで気づけない。
- 直し方: 仕組みで塞ぐ。既存の admin クライアント＋Postgres で完結する:

1) 送信記録テーブルを追加（migration 例）:
   create table sms_sends (id bigserial primary key, phone text not null, ip text, created_at timestamptz not null default now());
   create index sms_sends_recent on sms_sends (created_at desc);
   alter table sms_sends enable row level security;  -- ポリシーを作らない＝service_role以外触れない

2) startSmsVerification で Twilio を呼ぶ「前」に3段の上限を見る（超えたら送らず終了）:
   - 同一 phone: 直近1時間に3件まで
   - 同一 IP (request.headers.get("x-forwarded-for") をルートから渡す): 直近1時間に5件まで
   - 全体: 直近1時間に40件まで（この店の規模なら十分。請求が暴走しない天井）
   送信に成功したら sms_sends に1行 insert。

3) すでに用意済みの Cloudflare Turnstile を確認画面の送信ボタンに実際に配線する（環境変数は既にある）。

4) 併せて Twilio コンソール側で Verify のセグメント上限と月額スペンドキャップを設定する（運用ではなくアカウント側の固定上限なので、人が見張らなくても効く）。

## 3. [critical] 診断用エンドポイント /api/public/twstatus が本番に残存。固定文字列1つで、任意の電話番号へSMSを送信できる
- 場所: /home/user/abet-news/shippori-reserve/src/app/api/public/twstatus/route.ts:15
- 攻撃: このパスは src/middleware.ts:222 の `pathname.startsWith("/api/public/")` で認証チェックより手前に早期リターンされるため、ログイン不要で誰でも到達する。合言葉は文字列リテラル "shippori-8931" がソースにベタ書きされており、コミット eddf9ec0 でリポジトリ（j11046rk-commits/abet-news）に入っている。手順は3段:

```sql
create or replace function public.write_audit()
returns trigger language plpgsql security definer set search_path = public as $$
declare
  key_col text   := coalesce(tg_argv[0], 'id');
  pii     text[] := array['customer_name','customer_kana','phone','memo',
                          'allergy','invoice_name','source_detail','cancel_reason'];
  b jsonb := case when tg_op = 'INSERT' then null else to_jsonb(old) end;
  a jsonb := case when tg_op = 'DELETE' then null else to_jsonb(new) end;
  rec jsonb := coalesce(a, b);
  k text;
begin
  if tg_table_name = 'reservations' then
    foreach k in array pii loop
      if b ? k and b->>k is not null then b := jsonb_set(b, array[k], '"***"'::jsonb); end if;
      if a ? k and a->>k is not null then a := jsonb_set(a, array[k], '"***"'::jsonb); end if;
    end loop;
  end if;
  insert into audit_logs (actor, action, target_table, target_id, before, after)
  values (auth.uid(), tg_table_name || '.' || lower(tg_op), tg_table_name, rec ->> key_col, b, a);
  return coalesce(new, old);
end;
$$;

-- 既に貯まっているぶんを1回だけ洗う
update audit_logs
   set before = before - 'customer_name' - 'customer_kana' - 'phone' - 'memo'
                       - 'allergy' - 'invoice_name' - 'source_detail' - 'cancel_reason',
       after  = after  - 'customer_name' - 'customer_kana' - 'phone' - 'memo'
                       - 'allergy' - 'invoice_name' - 'source_detail' - 'cancel_reason'
 where target_table = 'reservations';
```

```sql
-- 人数・時刻・流入元・席・状態は残すので、売上と集計は無傷。

returns integer language plpgsql security definer set search_path = public as $$

begin

     set customer_name = '（保存期間経過）',  -- NOT NULL かつ空文字禁止(0004:12)なので置換する

end;
$$;
```

## 32. [low] flyers バケットが public かつ anon で中身を一覧できる（ポリシーに role 指定が無い）
- 場所: supabase/migrations/0028_event_flyer.sql:21
- 攻撃: `create policy flyers_public_read on storage.objects for select using (bucket_id = 'flyers');` には `to` 句が無いので、ロール PUBLIC＝anon にも適用される。バケット自体も public=true（0028:16）。

本番で確認済み:
$ curl -X POST 'https://ytqjgomnktkmoddidypd.supabase.co/storage/v1/object/list/flyers' \
    -H "apikey: <予約ページのJSに載っている anon key>" -H 'content-type: application/json' -d '{"prefix":"","limit":100}'
→ [{"name":"2026-08-14.jpg","metadata":{"size":843752,...}},{"name":"2026-08-15.jpg",...}]

ファイル名は uploadFlyer が `${date}.${ext}` 固定で付けている（src/app/(app)/calendar/actions.ts:112）ので、一覧しなくても総当たりで当たる。つまり「URLを知っている人だけ」という保護は最初から無い。
- 影響: 今バケットに入っているのはスタッフが上げたイベントのチラシ画像だけなので、個人情報は入っていない。実害は、まだ告知していない先の日付のイベントチラシ（内容・価格）が誰にでも先に見えること。
ただしこのポリシーは「バケットに入ったものは何であれ全世界に公開・列挙可能」という契約になっている。将来ここに予約台帳の写真や名簿PDFが1枚でも置かれた瞬間に、それがそのまま公開される。
- 直し方: バケットの用途をポリシー側で機械的に縛る。チラシは必ず `YYYY-MM-DD.拡張子` という名前なので、それ以外は出さないようにすればよい。

drop policy if exists flyers_public_read on storage.objects;
create policy flyers_public_read on storage.objects
  for select to anon, authenticated
  using (
    bucket_id = 'flyers'
    and name ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}\.(jpg|jpeg|png|webp|gif|heic|heif|pdf)$'
  );

これで「うっかり別のファイルを flyers に置いた」場合、そのファイルは配信も一覧もされない（列挙も同じ SELECT ポリシーを通るため）。運用ルールで「flyers に個人情報を置かない」と決めるのではなく、置いても出ない形にする。
