# 1. 全体設計

## 1-1. このシステムが答える問い

> **「今日、誰が何時に何名で来るのか。その予約を、どの席に通していいのか。」**

すべての画面はここから逆算する。開いた瞬間に「今日」が出る。登録は30秒で終わる。
分析は後からついてくる（が、そのためのデータは最初から取る＝**流入元は登録時に必ず記録する**）。

- **アプリとDBの間には必ず行レベルセキュリティ（RLS）を挟む**。「アプリのバグでURLを直接叩かれたら全予約が見えた」を構造的に防ぐ。
- **公開フォームからの書き込みだけは、サーバー側のAPI Route（service role）を経由**する。ブラウザに匿名の書き込み権限を一切渡さない。
- 既存の公式サイト（Astro／GitHub Pages）は**触らない**。予約フォームを1つ足すだけ。

## 1-3. 中核となる3つの考え方

### (A) 営業日（biz_date）が全ての軸

しっぽり亭は **18:00〜25:00**。24時をまたぐ。
「8月15日 24:30 の予約」は、カレンダー上は8月16日だが、店にとっては**8月15日の営業**である。

→ 予約・売上・席稼働はすべて `biz_date`（営業日）で束ねる。時刻は別に持つ。
→ 日付の境界で数字がズレる、という定番の事故を最初から潰しておく。

### (B) 営業モードは「日」の属性

```
                        business_days（営業日）
                       ┌──────────────────────┐
   mode = 'normal'  ←──┤  biz_date（主キー）    ├──→  mode = 'event'
   通常営業（しっぽり） │  is_busy（繁忙日）     │      イベント営業（ビアホール）
                       │  is_closed（休業）     │
   ・席ごとに管理       │  event_capacity       │      ・席は管理しない
   ・席割り当てルール適用 │  opens/closes         │      ・定員（総人数）だけ管理
   ・重複チェックあり    └──────────────────────┘      ・残席数＝定員−予約人数合計
```

- モードは**日単位**で切り替える。1日の中で混在させない（運用が破綻するため）。
- `business_days` に行が無い日は、**曜日から自動導出**（火曜＝休業、金土＝25時まで、それ以外＝24時まで、mode=normal）。
  予約が入るタイミングで行を実体化する（`ensure_business_day()`）。カレンダー画面は「まだ何も設定していない日」も正しく描ける。
- **繁忙日（`is_busy`）はモードとは別の軸**。通常営業のまま「今日は混む」を指定できる。席割り当てルールがこれを見る。

### (C) 席割り当ては「ルール＋人間の上書き」

```
  予約（2名・金曜）＋ 席候補（テーブル席=6名席）
            │
            ▼
   ┌─────────────────────────────────┐
   │ ルールエンジン                    │
   │ 条件：曜日 / 繁忙日 / 席定員 / 人数 │
   │ priority昇順で最初に一致した1件を採用│
   └───────────┬─────────────────────┘
               ▼
   allow（そのまま割当）
   warn （確認だけ出して割当可）
   deny （原則NG。ただし──）
               │
               ▼
   ┌─────────────────────────────────┐
   │ スタッフによる上書き（override）    │
   │ 理由の入力が必須。誰がいつ通したか記録│
   └─────────────────────────────────┘
```

**ルールは人を縛るためではなく、判断を助けるために置く。**
最終決定権は必ず現場のスタッフにある（denyでも理由を書けば通る）。
ただし通した記録は残る。あとで「金曜に2名を6人席へ通した回数」を数えられる＝ルールの妥当性を見直せる。

デフォルトで入れるルール（[03-database.md](03-database.md) の初期データ）：

| 優先度 | 名前 | 条件 | 判定 |
|---|---|---|---|
| 10 | 金土の少人数×大席は原則NG | 金・土 かつ 2名以下 かつ 席定員6以上 | **deny** |
| 11 | 繁忙日の少人数×大席は原則NG | 繁忙日 かつ 2名以下 かつ 席定員6以上 | **deny** |
| 50 | 平日は少人数でも大席OK | 日・月・水・木 かつ 席定員6以上 | **allow** |
| 90 | 席が大きく空きます | 3名以下 かつ 席定員6以上 | **warn** |

（ルールは画面から追加・編集できる。上表はあくまで初期値）

## 1-4. 予約のライフサイクル

```
                 ┌──────────┐
  HP/DM/LINE ──→ │ tentative │ 仮予約（未確認）
                 └────┬─────┘
   電話/直接 ────────→│（スタッフが内容確認）
                      ▼
                 ┌──────────┐        ┌────────────┐
                 │ confirmed │──────→ │  cancelled  │ キャンセル（理由を記録）
                 └────┬─────┘        └────────────┘
                当日 │
                      ▼
                 ┌──────────┐        ┌────────────┐
                 │  seated   │ 来店中  │  no_show    │ 無断キャンセル
                 └────┬─────┘        └────────────┘
                      ▼
                 ┌──────────┐
                 │ completed │ 会計済み
                 └──────────┘
```

- 電話・オーナー直通の予約は、登録時にいきなり `confirmed` にできる（スタッフが本人と話しているため）。
- HP予約フォームからは必ず `tentative` で入る。**自動で席は確保しない**（席が埋まっていても受け付けて、スタッフが折り返す運用）。
- `cancelled` / `no_show` の予約は席の重複判定から自動的に外れる。行は消さない（分析と、言った言わないの記録のため）。

## 1-5. 流入元の集約

| 流入元コード | 表示 | Phase 1 の入り方 | 将来 |
|---|---|---|---|
| `web_form` | ホームページ | 公開APIから自動 | 空席連動 |
| `instagram_dm` | Instagram DM | スタッフ手入力 | Graph API（要審査・[06-roadmap.md](06-roadmap.md)） |
| `line` | 公式LINE | スタッフ手入力 | Messaging API Webhookで受信箱へ自動投入 |
| `phone` | 電話 | スタッフ手入力 | — |
| `owner_direct` | オーナー直接 | スタッフ手入力＋**どのオーナーか**を選択 | — |
| `walk_in` | 当日飛び込み | スタッフ手入力 | — |

- 流入元は**必須項目**。ここを空にできる作りにしない（後から集計できなくなるため）。
- `owner_direct` はオーナー3名のうち誰経由かを `source_profile_id` で持つ。「誰の紹介がどれだけ効いているか」を数えられる。
- 集計は `biz_date × source` で常時集計可能（[04-api.md](04-api.md) `/api/stats/sources`）。

## 1-6. 権限モデル（後から細かく分けられる構造）

```
profiles.role ─→ role_permissions ─→ permissions
  (enum)          (行を足すだけ)       (権限コード)
```

- ロールは enum（`owner` / `manager` / `staff` / `viewer`）で始めるが、
  **「そのロールが何をできるか」はDBの `role_permissions` テーブルの行**で決まる。
- 「一般スタッフにも席ルールを編集させたい」→ **行を1つ足すだけ**。コードもマイグレーションも不要。
- RLS・API の両方が同じ `has_permission('reservation.write')` を見る。判定が2か所に散らない。

| ロール | 想定 | 初期の権限 |
|---|---|---|
| `owner` | オーナー3名 | すべて（アカウント発行・店舗設定・ルール編集を含む） |
| `manager` | 店長 | 予約・営業日・席ルールの編集。アカウント発行は不可 |
| `staff` | 一般スタッフ | 予約の登録・編集・席割り当て（上書き含む）、営業日の閲覧 |
| `viewer` | 閲覧のみ | 予約の閲覧のみ |

権限コード一覧は [03-database.md §permissions](03-database.md#3-3-権限permissions--role_permissions) 参照。

## 1-7. 個人情報の扱い（設計上の制約）

予約データには**氏名・電話番号**が入る。これは個人情報であり、扱いを最初から決めておく。

- アプリ全体を `noindex, nofollow` にし、未ログインは全ページ `/login` へリダイレクト（ミドルウェアとRLSの二重）
- 通信は全てHTTPS。Supabase の `service_role` キーはサーバー環境変数のみ（ブラウザに絶対に出さない）
- **監査ログ**（`audit_logs`）に予約の変更前後を記録。誰がいつ何を書き換えたかを追える
- 退職者はアカウントを `is_active = false` にすれば即座に読み書き不可（削除ではなく無効化。記録は残す）
- 保持期間：`completed` から**2年**を目安に、氏名・電話番号のみマスクする運用を推奨（集計用の人数・流入元は残す）
