# しっぽり亭 予約管理システム（shippori-reserve）

新居浜の居酒屋「しっぽり亭」の、**店舗予約を1つのダッシュボードに集約して管理する**ためのシステム。
**Phase 1（予約を1画面に集約）まで実装済み。** 設計ドキュメントは `docs/` に、アプリは `src/`、
DBのマイグレーションは `supabase/migrations/` にある。動かすまでの手順は下の「動かすまで」を参照。

## ひとことで言うと

> ホームページ・Instagram DM・公式LINE・電話・オーナー直通。
> **バラバラに入ってくる予約を、スタッフのiPhoneの中の1画面にまとめる。**

## 前提（依頼内容の要約）

- **業態は日単位で2つ**。
  - 通常営業（しっぽり営業）＝**席ごと**の予約管理
  - イベント営業（ビアホール営業）＝相席前提。席は管理せず**定員（総受け入れ人数）だけ**を管理
- **流入経路5つ**を集約：HP予約フォーム／Instagram DM／公式LINE／電話／オーナー3名への直接連絡
- 登録・編集は**ログインしたスタッフのみ**。ロールは**後から細かく分けられる**構造にする
- **席割り当てルール**を曜日・繁忙日ごとに設定でき、**スタッフ判断の上書き（オーバーライド）**を残す
- **PWA**。iPhoneの「ホーム画面に追加」でアプリのように使える
- 既存の[しっぽり亭ホームページ](https://shipporitei.jp/)（`site/`）と同じドメイン／プロジェクト配下に組み込む

また `dashboard.astro` の「共通パスワードで復号」方式は、**お客様の氏名・電話番号を扱う予約管理には使えない**
（誰が見たか記録できず、スタッフ個別の停止もできず、暗号化済みデータが誰でもダウンロードできる）。
→ **アプリは別プロジェクトとして作り、既存サイトとはリンクとAPIで繋ぐ**のが正解。詳細は [05-stack.md](docs/05-stack.md)。

## Phase 1 の実装（ここまで出来ています）

[06-roadmap.md](docs/06-roadmap.md) の Phase 1 =「**全経路の予約が1画面に集まる**」を実装しました。
まだ Supabase プロジェクトが無いので**動かすには下の「動かすまで」の作業が要ります**が、
コードとDBのマイグレーションは揃っています。

| 画面 | パス | 中身 |
|---|---|---|
| S0 ログイン | `/login` | ログインID＋パスワード。失敗理由は明かさない |
| S1 初回パスワード変更 | `/password` | 変えるまで他のどの画面にも入れない |
| S2 日別 | `/day/[date]`（今日は `/today`） | その日の時系列・要対応の先出し・来店/会計を1タップ・シフト編集 |
| S3 予約一覧 | `/reservations` | 期間・状態・流入元・フリーワード検索 |
| S4 予約登録 | `/reservations/new` | 電話で聞く順に並べた入力。**流入元は必須** |
| S5 予約詳細 | `/reservations/[id]` | 内容変更・状態遷移・キャンセル（理由必須） |
| S6 暦（ホーム） | `/` | **縦スクロールの1か月**。開いた位置は今日。シフトと受付者が一目で見え、日付ごとの＋からすぐ登録 |
| S7 営業日設定 | `/calendar/[date]` | 通常／イベントの切替・定員・繁忙日・休業・営業時間 |
| シフト | `/day/[date]` 内 | その日に誰が入っているかを名前チップで表示・タップで編集（店主フィードバック 2026-08-08 で追加） |
| S11 設定 | `/settings` | 店舗の既定値の確認・自分のパスワード変更 |
| S12 アカウント管理 | `/settings/accounts` | 発行・ロール変更・停止・パスワード再発行 |

- **PWA**：`manifest` ・アイコン・`env(safe-area-inset-*)`・`100dvh`・入力欄16px・Service Worker まで入っています。
  Service Worker はアプリの外枠だけをキャッシュし、**予約データは絶対にキャッシュしません**。
- **Phase 1 では席を割り当てません。** 予約の席欄は「T1」などを書けるメモです（`reservations.seat_note`）。
  重複判定つきの席管理は Phase 2（`reservation_seats` と排他制約）で入ります。
- 集計（S10）は Phase 4 なので、下タブはまだ4つです。データは Phase 1 の時点から正しく貯まります。

### 決めずに進めたこと（あとで変えられます）

実装を止めないため、以下は**既定値を置いて進めました**。どれも後から変えられます。

| 項目 | 置いた既定値 | 変える場所 |
|---|---|---|
| 公開URL | `yoyaku.shipporitei.jp`（サブドメイン案A）を前提 | Vercel のドメイン設定。既存サイトには触っていないので、案Bへは後から移行できます |
| イベント営業の既定定員 | **36名**（店主指定・2026-08-08） | `/settings` に表示。実体は `settings.default_event_capacity` |
| 標準滞在時間 | **120分** | 同上（`settings.default_stay_min`）。予約の終了時刻の計算に使います |
| 月額費用 | まず**0円**（Supabase Free + Vercel Hobby）で動かす前提 | 運用に乗ってから Pro（計約7,000円/月）へ。[05-stack.md §6](docs/05-stack.md#6-ランニングコスト) |

※ Vercel Hobby は規約上は商用不可です。**検証のうちは無料枠で、実際に店舗の業務で使い始める時点で Pro へ**、という順序を想定しています。

## 動かすまで（オーナーの作業が要るところ）

アカウント登録を伴う作業だけは、こちらでは代行できません。

1. **Supabase プロジェクトを作る**（リージョンは Tokyo）。
2. **`supabase/deploy-all.sql` を SQL Editor に貼って1回実行する**
   （0001〜0020 の結合済み。2026年6〜12月の売上目標データも一緒に入る。
   個別に流したい場合は `supabase/migrations/` を 0001→0002→0003→0004→0007→0008→0009→0011→…→0020 の順で）。
3. `.env.local.example` を `.env.local` にコピーし、Supabase の Settings > API から
   `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` を入れる。
   **`SUPABASE_SERVICE_ROLE_KEY` は絶対に他人に渡さないこと**（RLSを丸ごと無視できる鍵です）。
4. 初期アカウント9名を発行する。
   ```bash
   npm install
   npm run seed:accounts   # 初期パスワードが画面に1度だけ出ます。控えて口頭で渡してください
   npm run dev             # http://localhost:3000
   ```
5. Vercel にデプロイし、同じ環境変数を設定する（リージョン `hnd1`・Root Directory は `shippori-reserve`）。
   売上の自動取り込みを使う場合は `SALES_INGEST_TOKEN`（長いランダムな合言葉）も追加する。
6. DNS に `yoyaku` の CNAME を1行足して、Vercel のドメインに向ける（任意。まずは `〜.vercel.app` でも動く）。
7. **エアレジ実績の自動取り込み**：店のMacで shippori-report リポジトリの `APP-INGEST.md` の3手順
   （合言葉ファイル作成 → 過去実績837日の一括投入 → 毎朝7:30のlaunchd登録）。
   合言葉は手順5の `SALES_INGEST_TOKEN` と同じ値にする。

アイコンを作り直したいときは `npm run gen:icons`（`scripts/gen-icons.mjs` の SVG を書き換えてから実行）。

DBの守りが効いているかを確かめる SQL は [supabase/tests/](supabase/tests/) にあります
（**捨ててよいデータベースでだけ**流してください）。
