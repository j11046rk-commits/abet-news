# The Oldman — 運営ダッシュボード 機能仕様

愛媛県松山市の会員制プライベートクラブ「The Oldman」の運営ツール。
オーナー6名が共同出資して開設した施設（通称「秘密基地」）で、ポーカー・葉巻・ウイスキー・サウナを楽しむ。

## 0. このツールが答える唯一の問い

> **「今月、家賃を払えるのか。足りないなら、あと何回開催すればいいのか。」**

資金構造：

1. 施設で開催するポーカーゲームから **利用料（レーキ）** を徴収する
2. レーキを積み立て、**毎月約 ¥100,000 の家賃・光熱費** に充当する
3. 不足分はオーナー6名で分担する

すべての情報設計はこの問いから逆算する。ダッシュボードの第一画面は、
「積立額 / 目標」「不足額」「あと何回」「1人あたりの負担」だけで構成する。

## 1. ゴールと非ゴール

### ゴール

| # | 内容 | 測り方 |
|---|---|---|
| G1 | 開催実績とレーキ収入を、ゲーム終了直後にスマホから **30秒** で記録できる | `/sessions` の新規記録が、日時プリセット + 参加者インクリメンタル検索 + 金額チップで完結する |
| G2 | 積立残高と月次目標の達成状況が、**開いた瞬間** にわかる | `/` の最初のビューポート（375×667）に積立ゲージと不足額が収まる |
| G3 | 施設の利用予約を、6人でバッティングさせずに取れる | `/reservations` + `/calendar` で重複を検知し警告する |
| G4 | 出資者6名が金の流れをいつでも自分で確認できる（会計の属人化を防ぐ） | `/ledger` を member ロールも閲覧可（編集は owner のみ） |

### 非ゴール（v1では作らない）

- ハンドヒストリー・戦績分析（別プロダクトの領域）
- 決済・送金機能（現金精算が前提）
- 一般公開の集客サイト（クローズドな運営ツール）
- 通知（メール / LINE / Push）— v2 の拡張ポイント

## 2. 利用者と権限

| ロール | 人数 | できること |
|---|---|---|
| **オーナー（`owner`）** | 6 | 全機能。会計台帳の編集、固定費設定、施設設定、アカウント発行・管理、全予約の編集 |
| **メンバー（`member`）** | 可変 | 予約の作成と自分の予約の編集、セッション記録の入力、積立状況・台帳の**閲覧** |
| **ゲスト** | 記録のみ | アカウント不要。`players` テーブルに名前だけ登録される |

### 2-1. 認証方式：ログインID + パスワード

**LINEログインとマジックリンクは使わない。**

| 決定 | 内容 |
|---|---|
| 基盤 | Supabase Auth の email + password |
| 入力欄 | 「ログインID」と「パスワード」の2つだけ。メールアドレスは利用者に見せない |
| 変換 | `login_id` → `{login_id}@theoldman.local`。変換は **サーバー側 Route Handler のみ** で行い、規則をクライアントに露出させない |
| メール確認 | Supabase 側で Confirm email を **無効化**（`@theoldman.local` は実在しないドメイン） |
| 発行 | 自己サインアップ不可。オーナーが `/members` から発行。初期パスワードを生成して **画面に一度だけ表示**、オーナーが本人に手渡す |
| 初回ログイン | `profiles.must_change_password = true` の間は `/password` に強制リダイレクト |
| 忘れた場合 | オーナーが管理画面からリセット（新しい初期パスワードを再発行） |
| パスワード | 8文字以上。ハッシュは Supabase Auth に一任し、自前で保持しない |

サインアップ画面は作らない。未認証ユーザーはどのURLに来ても `/login` に飛ばす（`middleware.ts`）。

#### 認証まわりのエンドポイント

| メソッド | パス | 権限 | 役割 |
|---|---|---|---|
| POST | `/api/auth/login` | 誰でも | `login_id` + `password` を受け、内部で email に変換して `signInWithPassword`。Cookie にセッションを設定 |
| POST | `/api/auth/logout` | 認証済 | `signOut` |
| POST | `/api/auth/change-password` | 認証済 | 本人のパスワード更新 + `must_change_password = false` |
| POST | `/api/accounts` | owner | アカウント発行。初期パスワードを生成し **レスポンスに一度だけ** 返す |
| POST | `/api/accounts/[id]/reset-password` | owner | 初期パスワード再発行 |
| PATCH | `/api/accounts/[id]` | owner | ロール変更 / 有効・無効 / 表示名 / 出資額 |

`SUPABASE_SERVICE_ROLE_KEY` は Route Handler の中でのみ使用する。クライアントバンドルに絶対に入れない
（`NEXT_PUBLIC_` を付けない、`src/lib/supabase/admin.ts` は `import "server-only"` を先頭に置く）。

### 2-2. RLS

全テーブルで Row Level Security を有効化する。要点：

| テーブル | select | insert | update / delete |
|---|---|---|---|
| `profiles` | 認証済は全員 | owner のみ（実質 service role） | 本人 or owner |
| `players` | 認証済は全員 | 認証済 | owner |
| `sessions` / `session_players` | 認証済は全員 | 認証済 | 作成者 or owner |
| `reservations` | 認証済は全員 | 認証済（`created_by = auth.uid()`） | 作成者 or owner |
| `ledger_entries` | 認証済は全員（**閲覧は透明に**） | owner | owner |
| `fixed_costs` / `settings` | 認証済は全員 | owner | owner |

`is_active = false` のアカウントはログインできても何も書けない（ポリシーの述語に含める）。

## 3. 画面仕様

グローバルナビ（下部固定 / モバイル、上部 / デスクトップ）：
`ダッシュボード` `予約` `カレンダー` `セッション` `台帳` `メンバー`（`設定` は owner のみ）

### 3-1. ダッシュボード `/` — 最重要画面

上から順に：

1. **積立ゲージ** — 今月の積立額 / 月次目標（既定 ¥100,000）。縦型・液面が満ちる（§ DESIGN.md 5）
2. **不足額とリカバリー提案**
   - 「あと **¥32,000**」
   - 「平均レーキ ¥8,400/回 → **あと4回の開催** で達成」
   - 「今月残り **11日**」
   - 「このまま不足した場合、**1人あたり ¥5,334**」
3. **繰越残高** — 前月までの累計積立 − 累計支出
4. **直近のセッション3件** — 日付・種目・参加人数・レーキ額
5. **今週の予約** — 曜日ごとの横並びタイムライン
6. **記録するボタン** — 常時アクセスできる固定配置

#### 計算の定義（曖昧さを残さない）

- **今月の積立額** = 当月の `income` 合計 − 当月の `expense` 合計（＝当月収支）。
  マイナスなら 0 として扱いゲージは空。数値表示は実額（マイナス表示）。
- **不足額** = `max(0, monthly_target_yen − 今月の積立額)`
- **平均レーキ** = 直近90日の `sessions.rake_yen` の平均（セッション0件なら null → 「あと何回」は非表示）
- **あと何回** = `ceil(不足額 / 平均レーキ)`
- **1人あたり** = `ceil(不足額 / settings.owner_count)`
- **繰越残高** = 当月より前のすべての `income − expense`
- **残高がゼロを割る予測月** = 現在残高から、直近3ヶ月の平均月次収支を将来に外挿して初めて負になる月

### 3-2. セッション記録 `/sessions`

一覧 + 記録フォーム。**入力速度が最優先**。

- 記録項目：開催日時、終了時刻、種目（キャッシュ / トーナメント / その他）、参加者、レーキ合計、メモ
- 開催日時の既定は「今日 20:00」、終了時刻は空（未入力可）
- 参加者：マスタからのインクリメンタル検索 + 「新規ゲストとして追加」を **1タップ** で
- レーキ金額：`inputMode="numeric"` で数字キーパッドを直接呼ぶ + クイックチップ（+1,000 / +3,000 / +5,000 / +10,000 / クリア）
- 保存すると `ledger_entries` に `income / rake` の行が **自動起票** される（二重入力させない）
  - セッションを更新したら、紐づく台帳行も同期する
  - セッションを削除したら、紐づく台帳行も削除する

### 3-3. 予約 `/reservations`

施設の稼働を6人で共有するための中核機能。独立タブとしてグローバルナビの一等地に置く。

#### 入力項目

| 項目 | 仕様 |
|---|---|
| 日付 | 単日 |
| 時間帯 | **1時間単位**。開始・終了をプルダウン（00:00〜24:00、1時間刻み）。終了 24:00 は翌日 00:00 |
| 用途 | **複数選択（チェックボックス）**：ポーカー / ミーティング / プライベート / 宿泊 / その他 |
| 貸切希望 | **単独のチェックボックス** |
| 想定人数 | 数値（1〜30） |
| メモ | 任意。ただし用途に「その他」を含む場合は **必須** |

#### 貸切希望フラグ

用途タグの「プライベート」と貸切希望チェックは **別物**。混同させない。

- 用途の「プライベート」＝ 何をするかの分類（私用）
- **貸切希望** ＝ 他のメンバーに「この時間は来ないでほしい」と伝える意思表示

チェックボックスのラベル：

> ☐ **貸切にする** — この時間は他のメンバーの来訪をご遠慮いただきます

バッジ表示：

- **相席OK**（既定）— `--smoke` の細い枠線ラベル
- **貸切** — `--claret` の塗りつぶしラベル

**既定は相席OK。** この施設の価値は偶然の相席にもあるため、貸切は明示的な選択とする。

#### 一覧表示

- これからの予約を時系列で。過去分は折りたたむ
- 自分の予約は編集・削除可。他人の予約は閲覧のみ（owner は全編集可）
- 時間帯の重複は保存時に **警告する（ブロックしない）**。話し合いで解決する文化を尊重する
  - 既存予約が **貸切** の場合はより強い警告：「この時間は〇〇さんが貸切にしています。それでも予約しますか？」

### 3-3b. カレンダー `/calendar` — 独立タブ

予約状況を俯瞰するための専用画面。予約フォームとは分離し、単体で成立させる
（新しいブラウザタブで開いて常時表示しておける）。

- **月表示** / **週表示** を切替。既定は **週表示**
- 週表示：縦軸 1時間刻み、横軸 7日のタイムグリッド。予約はブロックとして描画
- 月表示：日ごとのマス目に、その日の予約を細いバーで積み上げる
- ブロックの見え方：
  - **色** = 用途（複数選択なら先頭の用途を主色に、ブロック下端に他の用途色の細いストライプ）
  - **塗り** = 貸切かどうか（貸切＝塗りつぶし / 相席OK＝枠線のみ・中は透過）
  - **テキスト** = 予約者名 + 用途
- 用途色（絵文字・アイコンは使わず、色と字間を広げた極小の大文字ラベルで区別）

  | 用途 | 色 |
  |---|---|
  | ポーカー | `--brass` `#B08D4F` |
  | ミーティング | `--smoke` `#7C766B` |
  | プライベート | `--claret` `#5A2028` |
  | 宿泊 | `#4A5A52`（深緑） |
  | その他 | `#3A3632` |

- 凡例は常時表示せず、小さなトグルに収める
- ブロックをクリック → 詳細ポップオーバー。自分の予約なら編集へ
- 空きスロットをクリック / ドラッグ → その時間帯で予約フォームが開く（1時間単位にスナップ）
- 「今日」に戻るボタンと前後移動を必ず置く
- モバイルでは週表示を **3日表示** に自動で切り替える

### 3-4. 会計・積立 `/ledger`

- 収支台帳（日付、区分、カテゴリ、金額、メモ、紐づくセッション）
- カテゴリ
  - 収入：レーキ / ゲストフィー / ドリンク / 出資・追加拠出
  - 支出：家賃 / 光熱費 / 備品 / その他
- 月次推移グラフ（収入・支出・残高）— 自作SVG
- 固定費マスタ（家賃・光熱費など、毎月自動で支出計上）
- 「残高がゼロを割る予測月」を警告として表示

固定費の自動計上は、当月分が未計上なら台帳画面を開いたときに owner に「計上する」ボタンを出す方式
（cron を持たない構成のため。§ ISSUES.md）。

### 3-5. メンバー `/members`

- オーナー6名の出資額、参加回数、直近参加日
- ゲストを含む参加者マスタの一覧
- **アカウント管理**（owner のみ）：新規発行、ロール変更、パスワードリセット、無効化

#### 貸切時間の集計

**この施設に利用時間の縛りはない。罰則も上限も設けない。**
ただし、誰がどれだけ独占していたかが全員に見えている状態を作る。ルールではなく可視化で自律を促す。

- 集計対象：`is_exclusive = true` の予約の **実時間の合計**
- 集計単位：アカウントごと × 今月 / 今年 / 通算
- 表示：メンバー一覧の各行に横棒。全員分を同一スケールで、多い順に
- 数値は `12.0 h` のように `IBM Plex Mono` の tabular-nums で
- 参考値として **貸切でない利用時間** も併記し、貸切だけが目立ちすぎないようにする
- コピーは中立に。評価語を使わない
  - ○「貸切利用 — 今月」
  - ×「独占時間ランキング 🏆」「注意：使いすぎです」

### 3-6. 設定 `/settings` — owner のみ

月次目標額、施設名、レーキルールの記述、オーナー人数、タイムゾーン（`Asia/Tokyo` 固定・表示のみ）。

## 4. データモデル

`supabase/migrations/` にマイグレーションSQLとシードデータを置く。
金額はすべて **円の整数（`integer`）**。小数は使わない。

| ファイル | 内容 |
|---|---|
| `0001_schema.sql` | enum / テーブル / 制約 / インデックス |
| `0002_views.sql` | `v_monthly_summary` / `v_session_stats` / `v_exclusive_hours` |
| `0003_rls.sql` | RLS 有効化とポリシー |
| `0004_seed.sql` | 初期設定 + 固定費 + オーナー6名分のプレイヤー + 過去3ヶ月のダミーセッション |

スキーマ本体は指定どおり（`profiles` / `players` / `sessions` / `session_players` /
`reservations` / `ledger_entries` / `fixed_costs` / `settings`）。

### ビュー

- `v_monthly_summary` — 年月ごとの収入合計・支出合計・当月収支・累計残高
- `v_session_stats` — セッションあたりの平均レーキ、直近30日の開催頻度
- `v_exclusive_hours` — アカウント別・年月別の貸切利用時間 / 通常利用時間（時間・小数第1位）

### 1時間単位制約についての注記

`date_trunc('hour', starts_at) = starts_at` は UTC 基準で評価されるが、
JST は UTC+9（分のオフセットを持たない）ため、JST の毎正時は UTC の毎正時と一致する。
したがってこの制約で「JST 1時間単位」を正しく担保できる。

## 5. 技術スタック

- **Next.js 15 / App Router / TypeScript**
- **Tailwind CSS v4** — デザイントークンは CSS 変数で定義し、`@theme` から参照
- **Supabase**（Auth / Postgres / RLS）
- 日時は `date-fns` + `date-fns-tz`、`Asia/Tokyo` 固定
- グラフは **自作SVG**（Recharts は使わない）
- デプロイ：**Vercel**（GitHub 連携、main への push で自動デプロイ）
  - `middleware.ts` で未認証アクセスを全て `/login` へ。URLが漏れても中身が見えない
  - 環境変数は Vercel の Environment Variables に登録。`SUPABASE_SERVICE_ROLE_KEY` はサーバー側のみ

> 元プロンプトの §9 に「Cloudflare Pages にデプロイ済み」とあるが、§5 の
> 「Vercel にデプロイ」と矛盾する。**Vercel を採用**した（Next.js App Router +
> Route Handler + middleware の対応が素直なため）。Cloudflare Pages へ載せる場合の
> 差分は HANDOFF.md に記す。

## 6. 非機能要件

- **モバイルファースト**。375px 幅で完全に成立させる
- キーボードフォーカスリングを可視化（真鍮の 2px アウトライン）

- タイムゾーンは `Asia/Tokyo` 固定
- 環境変数は `.env.local.example` に雛形。実値はコミットしない
