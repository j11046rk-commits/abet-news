## 2026-08-06（第3回）

### 直したもの

- **月次目標の分母が誤っていた（重大）**
  ダッシュボードの達成額に `v_monthly_summary.net_yen`（全収入 − 全支出）を使っていた。
  月次目標 ¥100,000 は「家賃＋共益費＋水道光熱でおよそ10万円かかるから、それをレーキで
  賄う」という意味の数字なので、比べる相手は稼いだ金でなければならない。net_yen だと
  - 出資（¥600,000）が達成額に混ざり、一晩で目標達成に見える
  - 家賃を支出計上した分だけ達成額が下がり、10万円のために20万円必要になる
  という二重の誤りが出ていた。`operating_income_yen`（出資を除いた収入）を view に足し、
  そちらで測るようにした（0009）。

- 台帳を通帳形式にした。日付・名目・入金・出金・残高。月ごとに切り替え、
  各月の先頭に前月繰越を出す。金額は等幅・右揃えで桁を揃えた。
- 固定費を家賃・共益費の2件に絞り、計上日に pg_cron で自動起票するようにした（0009）。
  自動起票された行は台帳から直接いじれない（RLS でも弾く）。金額はマスタ側で直す。
- 立替メモ（0009）とほしい物リスト（0010）を追加。
- 水道代・電気代の未記帳アラート（0011）。請求が翌月に来るので開始月は対象外。
- 更新ボタンをタブ列からマストヘッドへ移した。タブに混ぜると「別の画面へ行くもの」に見える。
- 積立ゲージを写真ベースに作り直した。手描きSVGでは厚いガラスの質感が出なかった。

### 2026-08-06（第5回）— リストの画像添付が保存できなかった

**症状**：画像を付けて保存を押すと、いつまでも「保存中」のまま戻らない。

**原因は2つ重なっていた。**

1. Next.js の Server Action の本文上限が既定で 1MB。スマホの写真は 3〜4MB あるので
   `Body exceeded 1 MB limit` で 500 が返っていた。実測（4032×3024 / 3.3MB）で再現。
2. クライアントが Server Action の例外を拾っていなかった。500 で reject されると
   `setBusy(false)` に到達せず、ボタンが「保存中」のまま二度と戻らなかった。
   つまり「重い」のではなく、失敗したまま黙って固まっていた。

**直し方**：上限を上げるのではなく、画像をサーバに通さない形にした。

- ブラウザで長辺1600pxまで縮めて WebP に詰め直してから送る（3.28MB → 522KB / 400ms）。
- 縮めたものをブラウザから直接バケットへ上げ、Server Action にはパス文字列だけ渡す。
  スマホ→Vercel→Supabase と同じバイト列を2回運んでいたのが1回になる。
- submit 全体を try/catch で囲み、何が起きてもボタンが戻るようにした。
- 行の作成に失敗したら、上げた画像を消す（誰からも辿れないゴミを残さない）。

**ついでに塞いだ穴**：バケットの insert ポリシーが「会員なら誰でも書ける」だったので、
他人のIDのフォルダにも置けてしまっていた。先頭フォルダが本人のIDであることを
要求するようにした（0012）。読み取りと削除は会員全員のまま — 共有リストなので
他人の品の画像も見えるべきだし、消された行の画像が残らないようにするため。

**未検証**：サンドボックスのブラウザから *.supabase.co へ出られない（CAを入れられない）ため、
ブラウザでの通しの成功は確認できていない。圧縮はブラウザで実測、アップロードと
RLS は同じ anon キー＋ユーザーセッションで Node から確認した。

### 2026-08-06（第7回）— リストの画像がまだ遅かった

第5回の直しで「保存できない」は解けたが、まだ遅いという指摘。2つ原因があった。

1. **Vercel の関数が iad1（ワシントン）で動いていた。** DB は ap-northeast-1（東京）
   なので、画面を1枚描くたびに 日本 → 米東海岸 → 東京 → 米東海岸 → 日本 を往復して
   いたことになる。リストに限らずアプリ全体の遅さの元。
   `vercel.json` には最初から `regions: ["hnd1"]` と書いてあったが、この指定は
   Hobby プランでは効かず、プロジェクト設定の側が iad1 のままだった。
   Management API で `serverlessFunctionRegion` を hnd1 に変更した。
   **設定側の値が正であって、リポジトリの記述は効いていない** — 次に迷わないよう記す。

2. **画像を WebP で詰めていた。** 手元の計測（4032×3024 / 3.3MB → 1280px）で
   JPEG q0.75 が 280KB / 47ms、WebP q0.75 が 250KB / 200ms。容量はほぼ同じで
   エンコードが4〜6倍遅い。さらに iOS 17 より前の Safari は canvas から WebP を
   書き出せず、失敗もせずに PNG を返す。写真の PNG は元より大きくなるので
   「縮まなかったから元のまま送る」という分岐に落ち、結局3MBを送っていた可能性が高い。
   JPEG に切り替え、出てきた MIME が頼んだものと違うときはそこで諦めるようにした。
   長辺も 1600 → 1280 に落とした（サムネイルは実寸56px）。

ついでに `createImageBitmap` に `imageOrientation: "from-image"` を付けた。
これが無いと iPhone の縦位置の写真が横倒しのまま焼き込まれる。

### 2026-08-06（第8回）— 瓶が小さい・注ぎ終わりが不自然

- **瓶が指定どおり大きくならなかった。** 全体に効いている `img { max-width: 100% }` が
  効き、`width: 150%` を指定してもグラスの幅で頭打ちになっていた。`max-width: none` を
  明示。座標もブラウザで実測し直し、注ぎ口と筋の始点が同じ点（63, 5）に来るようにした。
- **注ぎ終わったあと、瓶が倒れたまま去っていた。** 立ててから持ち上げるようにした。
  ただし軸が注ぎ口にあるため、その場で立てると瓶の本体がグラスの中へ倒れ込む
  （注ぎ口を下端にして体が真下へ伸びるため）。立てる動きと持ち上げる動きを
  同じキーフレームに入れて解決した。

**アニメーションを目で確かめる手順**（毎回ここで手間取るので残す）:
`animation: none` を入れて reflow を挟み、戻してから `animationPlayState: paused` と
負の `animationDelay` を設定すると任意の時点で止められる。
単に負の delay を足すだけでは、既に終わったアニメーションは巻き戻らない。

### 2026-08-06（第9回）— 注ぎの筋が細く、直線的だった
